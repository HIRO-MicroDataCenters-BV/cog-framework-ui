Project Context

CAPE — Rethinking Edge Computing Architecture

CAPE (Compute Architecture for Powerful Edge) is an EU Horizon Europe project that rethinks disaggregated, hyperconvergent computing across the full cloud-edge spectrum to strengthen European digital sovereignty. HIRO contributes both hardware (EMDC) and the intelligent software orchestration layer, with the Cognitive Framework powering the AI decision agent for workload placement.

Project Goals
  • Strengthen European digital sovereignty
  • Disaggregated, hyperconvergent computing at edge
  • Open-source software stack for cloud-edge
  • Composable infrastructure & thermal management
  • AI-assisted deployment and orchestration
  • Support diverse application domains

Cognitive Framework (CF) — Role in CAPE

CF as the AI Decision Agent for Workload Placement: In CAPE, HIRO's Cognitive Framework plugs into the hiro-adaptive-orchestrator as the external AI decision agent. The orchestrator calls CF via HTTP to score candidate Kubernetes nodes for pod placement. CF runs ML inference, returns per-node scores (0–100), and the scheduler normalises these into placement decisions — enabling ML-driven, energy-aware, resource-aware workload orchestration at the edge.

What CF Provides to CAPE

  • AI Decision Agent — HTTP endpoint at /api/v1/agent/placement/decision · receives DecisionRequest · returns per-node scores [0–100]
  • Energy forecasting model — Linear Regression (energy_forecasting_linear_regression.pkl) trained on CPU + memory metrics via Kepler/eBPF · predicts future energy availability in Watts
  • Model registry (MLflow) — versions energy forecasting and placement scoring models; supports retraining via Jupyter notebooks
  • Model serving (KServe) — serves AI agent as inference endpoint within the CAPE cluster
  • Experiment tracking — logs placement quality, energy consumption, and scheduling outcomes across CAPE deployments
  • Federated Learning — enables energy and placement models to improve across multiple EMDC sites without centralising sensitive operational data

CF Lifecycle in CAPE

1 · Train Energy Model Kepler (eBPF) collects node power data → Prometheus → PostgreSQL → CF trains Linear Regression model → logs to MLflow registry
2 · Register & Serve cogflow.pyfunc.log_model() registers model → cogflow.serve_model_v2() deploys as KServe InferenceService (AI Decision Agent)
3 · Score Placement hiro-adaptive-orchestrator sends POST /api/v1/agent/placement/decision to CF agent → CF scores candidate nodes considering energy, CPU, memory, GPU
4 · Schedule Scheduler plugin normalises CF scores [0,100] → [0,10] → Kubernetes places pod on optimal node per OrchestrationProfile strategy (Balanced / Packed / Spread)
5 · Federated Update Placement outcomes and energy metrics federated back to CF across CAPE EMDC sites → global model improves without sharing raw cluster data

CF as IaC Governance — Cognitive Validator (act)

Beyond ML orchestration, CF extends into infrastructure code governance via the act IaC Agent. The Cognitive Validator is an optional LLM layer (LangGraph + CF-served LLM) that runs alongside deterministic security rules to analyse Pulumi program content before any resource is provisioned.

  • CF role: serves the LLM endpoint consumed by the Cognitive Validator; non-blocking if unreachable
  • LangGraph: orchestrates multi-step reasoning over resource declarations
  • Secret detection: LLM scans string fields for embedded API keys, tokens, passwords
  • Shell safety: analyses user_data scripts for unsafe commands before cloud execution
  • Additive: runs after deterministic Checkov/OPA rules — LLM catches semantic risks rules miss

CAPE-Specific Integration

  • CAPE provider schema: tests/fixtures/cape/schema.json — validates CAPE-specific Pulumi resource declarations
  • cape-sdks submodule: CAPE SDK bindings integrated as git submodule for provider validation
  • Target architectures: amd64 · arm64 · RISC-V · GPU · FPGA · CXL — all validated before deployment to EMDC nodes
  • Fuzzing: atheris + hypothesis property testing for edge-case IaC config detection
  • Checkov adapter: bridges act findings into standard security scanning workflows
  • k3s test targets: local cluster validation before CAPE edge deployment

C-Suite Takeaways
🧠
HIRO's CF is the AI brain of CAPE's orchestration layer The Cognitive Framework serves as the external AI decision agent for the CAPE adaptive orchestrator, scoring Kubernetes nodes based on real-time CPU, memory, GPU, and energy data. This makes HIRO the only partner delivering both hardware (EMDC) and the AI intelligence layer for the entire CAPE platform.
⚡
Energy-aware AI scheduling — unique CF capability in CAPE HIRO trained a Linear Regression model (hosted in CF/MLflow, served via KServe) that predicts future energy consumption from Kepler eBPF metrics. The energy-aware orchestrator uses this CF model to defer non-critical workloads to renewable energy windows — a novel green-computing contribution directly enabled by the CF.
🔗
Decentralised control plane — novel Rust + P2P architecture The mesh-controller (Rust, p2panda P2P, Ed25519) and placement-controller together form CAPE's decentralised control plane — no single point of failure, no central authority. CF model updates federate across EMDC sites via this P2P mesh, enabling distributed AI without centralising operational data.
🛰️
Three high-value use cases demonstrate HIRO's full stack HIRO's EMDC hardware + CF AI orchestration is deployed across Smart Grid (IPTO), Edge AI (Fraunhofer), and Satellite Data Processing (PCBD) use cases — covering energy, computer vision, and Earth-observation domains. This validates HIRO's platform as domain-agnostic and production-ready.
🛡️
CF now governs infrastructure code — not just ML workloads The act IaC Agent (CF-powered Cognitive Validator) extends CF beyond ML serving into DevSecOps. A LangGraph + LLM layer intercepts Pulumi infrastructure declarations before cloud deployment, detecting embedded secrets and unsafe shell commands in user_data. CAPE's provider schema and cape-sdks are integrated as a first-class test target — with coverage across amd64, arm64, RISC-V, GPU, FPGA, and CXL node types. This means CF is now a governance layer for both AI models and infrastructure code.
🔄
CF reuse across VERGE, ACES, NextGen and CAPE = compounding IP value The same Cognitive Framework (cogflow, KServe, MLflow, KFP) deployed in VERGE and ACES now powers CAPE's AI orchestration layer. Each project adds new CF capabilities (energy forecasting, federated placement, NTK fine-tuning) that feed back into the platform — increasing HIRO's IP value and reducing per-project engineering cost.
