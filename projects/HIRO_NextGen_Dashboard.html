Cognitive Framework (CF) — Role in NextGen

How HIRO's CF Connects to the NextGen Platform

In NextGen, HIRO's Cognitive Framework (CF) sits above the Data Space Node: the Data Space Node governs who can access what data, while the CF orchestrates what ML happens with that data. Together they form HIRO's complete federated intelligence stack for healthcare.

CF Provides to NextGen
  • Federated Learning across clinical sites (ki, hus, uva) without moving raw patient data
  • ML pipeline orchestration (Kubeflow Pipelines) for genomic & multimodal models
  • Model registry (MLflow) for versioning trained genomic/clinical models
  • Model serving (KServe) for deploying inference endpoints at edge sites
  • LLM fine-tuning via NTK (cf_finetune_ntk) for AI-guided genomic curation tasks
  • Experiment tracking across distributed training runs
Data Space Node Enables CF
  • ds-connector exposes governed clinical/genomic datasets to CF training pipelines
  • ds-policy-engine (OPA) authorises which CF jobs can access which datasets
  • ds-contract-engine issues time-limited VC-JWT contracts for CF model training runs
  • rhio (P2P) syncs model weights and training artifacts between CF instances across sites
  • ds-catalog makes CF-trained models discoverable as catalog items for partner reuse
CF Models & Pipelines in NextGen
  • Federated genomic ML: PRS, GWAS models trained across sites via CF FL
  • LLM fine-tuning: Qwen2.5-0.5B-Instruct fine-tuned with NTK (signed-log-mask controllers, LoRA-free) for AI-guided variant curation
  • Anomaly detection: metrics-anomaly-detection (Python) for platform health monitoring
  • Multimodal models: clinical + genomic data fused via CF pipelines using MMIOs
  • All models versioned in CF MLflow registry, served via KServe at each clinical site
CF Lifecycle — Federated Model Training in NextGen
1 · Discover Data Researcher finds genomic dataset via ds-catalog / ds-search-service — CF pipeline queries catalog to locate training data across ki, hus, uva sites
→
2 · Authorise CF training job authenticated via DEX-DKMS (KERI DID) · ds-policy-engine evaluates OPA rules · ds-contract-engine issues time-limited training contract
→
3 · Federated Train CF runs KFP pipeline locally at each site via ds-connector — local model trained on local data · no raw data leaves the site · weights only exchanged
→
4 · Aggregate rhio (P2P) syncs model weights / gradients across sites · CF aggregates into global model · MLflow tracks experiment versions
→
5 · Register & Serve Global model registered in CF MLflow registry · cogflow.serve_model_v2() deploys to KServe at each edge site · Listed in ds-catalog for partner discovery
→
6 · Fine-tune (LLM) cf_finetune_ntk: Qwen2.5-0.5B fine-tuned with NTK (LoRA-free) for genomic curation · CogAPI manages dataset + ISVC deployment · vLLM serves inference
Key distinction vs VERGE/ACES: In NextGen, CF operates in a federated learning mode across geographically distributed clinical sites, with the Data Space Node enforcing data governance (who can train, on what, for how long) before any CF pipeline runs. The Data Space Node + CF together form HIRO's full sovereign AI stack.
Project Context

NextGen — Personalised Cardiovascular Medicine via Federated Data

The NextGen project builds a small-scale European Health Data Space (EHDS) that lets researchers connect securely across global genomic and clinical datasets without centralising sensitive patient data. HIRO provides the technical infrastructure backbone: the Data Space Node platform and edge compute hardware (PEaaS).

Clinical Focus
  • Cardiovascular disease prediction & prevention
  • Diagnosis & treatment personalisation
  • Polygenic risk scores (PRS) across federated sites
  • Genome-wide association studies (GWAS)
  • Differential gene expression analysis
  • 6 pilot demonstrations · 5 clinical sites
Data Types
  • Genomic variant data (WGS/WES)
  • Clinical EHR records
  • Multimodal Integration Objects (MMIOs)
  • Imaging & biosensor data
  • Federated catalogue metadata
  • Consent & governance records
HIRO's Role

Data Space Data Flow — Federated Dataset Access

How a researcher accesses a genomic dataset across a federated NextGen clinical site:

1 · Discover Researcher searches via nextgen-fe portal → queries ds-search-service which aggregates results from all federated ds-catalog nodes
→
2 · Authenticate DEX-DKMS verifies researcher identity via KERI AID / decentralised DID → issues OIDC token to access platform
→
3 · Authorise ds-policy-engine evaluates OPA/Rego policies → checks role & institute → grants or denies access to specific dataset
→
4 · Contract ds-checkout processes order → ds-contract-engine mints time-limited VC-JWT access contract signed with Ed25519
→
5 · Access Data ds-connector requests data from local site data layer → returns data to authorised researcher via REST API under contract
→
6 · Sync rhio replicates catalog updates / result objects across sites via P2P (p2panda) + NATS JetStream without central broker

C-Suite Takeaways
🏗️
HIRO built the entire Data Space Node platform for NextGen HIRO engineered 10+ microservices (catalog, search, connector, checkout, policy, contracts, identity, P2P messaging, frontend) forming the complete technical backbone of the NextGen federated health data infrastructure — deployed at 3 clinical sites across 3 continents. The CF sits on top of this stack to deliver federated AI.
🔐
Novel technology: Decentralised identity (KERI/DID) for healthcare HIRO developed DEX-DKMS — a production-ready KERI-based decentralised identity bridge using Ed25519 cryptography. This is cutting-edge SSI (Self-Sovereign Identity) technology rarely deployed at scale, giving HIRO advanced IP in the health data sovereignty space.
⚡
rhio: Novel Rust-based P2P data exchange without central infrastructure HIRO built rhio — a Rust-based peer-to-peer message routing and S3 file sync system using p2panda and NATS JetStream. This eliminates the need for central brokers in federated health data networks, a key sovereignty and resilience requirement for the EHDS.
📋
Full compliance stack: OPA policies + VC-JWT contracts + GDPR governance HIRO implemented the entire governance layer: OPA/Rego policy engine, VC-JWT contract issuance/validation with Ed25519 signing, and partner feedback loop. This makes HIRO's platform GDPR-compliant and ready for regulated healthcare environments across 7 countries.
🔄
Reusable platform assets across EU projects The Data Space Node components (catalog, connector, policy engine, contract engine, rhio) are all open-source (MIT) and independently deployable. They can be reused across other EU Data Space initiatives (GAIA-X, Health Data Space, IDSA) — multiplying HIRO's commercial opportunities beyond NextGen.
